## What we learned

The automation that's supposed to be running this studio in maintenance mode is itself broken.

This week the daily log sessions revealed a recurring git infrastructure bug: each scheduled run is starting in detached HEAD. That means commits go to a floating, unnamed state rather than to `main`. They look like they went through — the session commits, reports success, moves on — but they're stranded. Nobody sees them until someone manually recovers them.

This week alone, six commits piled up in detached HEAD between October 31 and November 5. They got recovered on November 5 via cherry-pick, but the root cause isn't fixed. Next week's sessions will start detached again. The commits will strand again.

This matters for a specific reason: the daily log is the studio's only active output. Code isn't shipping. Products aren't deploying. The newsletter isn't going out. The daily log is what's supposed to be standing watch — tracking what's happening (or not happening), surfacing what needs attention, maintaining a paper trail. If the daily log is committing to nowhere, the studio doesn't just have a productivity problem. It has a visibility problem. The watch isn't working.

The Mastra P1s are now at 56 weeks on a live system. Last week's draft spent the deep dive on 49 weeks. The week count will keep going up unless the work gets done.

## Deep dive: when automation hides the problem

The detached HEAD issue is worth unpacking because of what it illustrates about automated systems generally.

The scheduled daily log was set up to do something simple: commit a markdown file to `main` every day. That's it. No builds, no deploys, no external calls. It should be the most reliable piece of infrastructure in the studio.

But somewhere in the environment configuration — the way the scheduled container starts, the git state it inherits — the HEAD reference isn't attached to a branch. The session runs, writes the file, commits it, and reports success. Everything looks fine from inside the session. The commit hash exists. The file is there. No errors.

What's missing is that the commit went to a detached HEAD position, which means it has no branch parent. Git doesn't surface this as an error — a detached commit is valid git state. It's just not visible to `git log` on `main`, not pushed to origin in the normal way, not part of the history anyone looking at the repository would see.

This is the specific failure mode of automation that reports completion without verifying outcome. The session's job was to commit a file. It committed a file. Done. What it didn't do was check whether that commit was actually on the right branch, actually visible to the repository, actually doing the thing the commit was supposed to do.

It's the same failure mode that shows up in product work: a feature gets built, the ticket gets closed, but nobody checked whether the feature actually works for users in production. The metrics say shipped. The reality says broken.

The fix here is a pre-commit branch check — verify HEAD is attached to `main` before writing anything, abort and alert if it isn't. That's a two-line shell script. The delay isn't technical.
